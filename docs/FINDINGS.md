# 実機での測定記録

`diag.html` を実機で動かして得た結果をまとめたものである。
仕様や解説記事ではなく、ここでの測定値を設計の根拠にしている。

測定したのは iPhone 1 台のみで、環境は iOS 18.7、Safari 26.6.1 である。
**機種名を記録していない。** カメラの上限が 4032×3024 であることは分かっているが、
どの機種のものかは特定できていない。以降の値は 1 台での結果にすぎない。

---

## わかったこと

### カメラで取得できるもの

| 項目 | 結果 |
| --- | --- |
| 最大の解像度 | 2160×3840、毎秒 30 コマ |
| 毎秒のコマ数 | 1 から 60 まで指定できる |
| ズーム | 0.5 倍から 10 倍。0.5 倍では超広角のレンズに切り替わる |
| ライト | 操作できる |
| ホワイトバランス | 自動と手動を選べる |
| 露出 | 指定できない。露出を変えながら複数枚撮る方法は使えない |
| 写真として撮れる最大 | 4032×3024 |

解像度を横向きの値で要求しても、縦向きの値で返る。要求した値ではなく、
`getSettings()` が返す値を常に使っている。

「iOS Safari では 720p までしか取得できない」という記述を各所で見かけるが、
少なくともこの端末では当てはまらない。

### 1 コマを取り出す方法

480×640 での測定値である。

| 方法 | 所要（中央値） | 向き |
| --- | --- | --- |
| `drawImage` | 0 ミリ秒 | 映像と同じ |
| `new VideoFrame(video)` | 0 ミリ秒 | **回転している（640×480 が返る）** |
| `ImageCapture.grabFrame()` | 34 ミリ秒 | 映像と同じ |

`grabFrame` は遅く、`VideoFrame` は向きが違う。どの方法を使うかは端末によって変わるため、
起動時に実際に測り、映像と同じ向きで返るもののうち最も速いものを選んでいる。

### 写真API と通常撮影の比較

同じ場面を両方の方法で撮った結果である。輪郭の量はラプラシアン分散、
ノイズは平らな部分の標準偏差で、いずれも中央の 512×512 を対象にしている。
所要と輪郭の値は、撮影した順に 1 枚目、2 枚目、3 枚目を並べたものである
（矢印は 1 枚目から 2 枚目への変化を示す）。

| 映像の解像度 | 撮影方法 | 解像度 | ファイルの大きさ | 所要 | 輪郭 | ノイズ |
| --- | --- | --- | --- | --- | --- | --- |
| 720×1280 | 写真API | 同じ | 631KB | 1408 → 335、348 ミリ秒 | 1868、1927、1898 | 1.67 から 1.98 |
| | 通常 | 同じ | 377KB | 45 ミリ秒 | 2124 | 1.78 |
| 1080×1920 | 写真API | 同じ | 1.2 から 1.6MB | 1024 → 378、361 ミリ秒 | 2275、3554、4569 | 2.14 から 3.46 |
| | 通常 | 同じ | 790KB | 51 ミリ秒 | 2620 | 2.23 |
| 2160×3840 | 写真API | 同じ | 3.9 から 6.9MB | 1236 → 589、571 ミリ秒 | 518、2146、2225 | 1.43 から 5.43 |
| | 通常 | 同じ | 2.77MB | 214 ミリ秒 | 1485 | 2.38 |

読み取るうえでの注意が 3 つある。

1. ラプラシアン分散はノイズも輪郭として数える。写真API で輪郭の値が高い回は
   ノイズの値も上がっており、実際に解像しているとは言い切れない。
2. 写真API で 3 枚撮ってから通常撮影を行っているため、露出の条件が揃っていない。
3. 各段の 1 枚目だけ傾向が違う。4K の 1 枚目は輪郭が 518 で、明らかに甘い。
   写真の撮影処理は、焦点と露出が落ち着く前に 1 枚目を撮っていると考えられる。

**結論として、写真API に解像度の利点は無く、所要時間は通常撮影の 5 倍から 10 倍に達する。**
画質の優劣にも決め手が無いため、通常撮影を既定にしている。

### 写真API に指定できる大きさ

| 指定した大きさ | 結果 |
| --- | --- |
| 1 倍（2160×3840） | 2160×3840 |
| 1.5 倍（3240×5760） | 2160×3840 に調整される |
| 2 倍（4320×7680） | 2160×3840 に調整される |
| 端末の上限（4032×3024） | 失敗する（`IPC Connection closed`） |

失敗するのは端末の上限を指定したときだけである。この値は映像と縦横比が違う。
大きさを指定しても得られるものが無いため、アプリからは指定していない。

### シャッター音

写真API による撮影では、720p、1080p、4K のいずれでも**鳴らなかった**。
この端末はスクリーンショットでは音が鳴るため、日本国内向けの端末だと分かる。

WebKit のソースを確認したところ、音を止める処理は存在しない。
`AVVideoCaptureSource::photoConfiguration()` は
`photoSettingsWithFormat:{AVVideoCodecKey: JPEG, AVVideoQualityKey: 1}` を組み立てて
`capturePhotoWithSettings:` に渡すだけで、シャッター音の抑止には触れていない。
つまり WebKit が止めているのではなく、この経路が音の対象から外れているだけである。
Apple が意図した挙動とは限らないため、将来の iOS で鳴るようになる可能性がある。

### 保存できる形式

| 形式 | 指定したときの `blob.type` | 実際の中身 |
| --- | --- | --- |
| JPEG | `image/jpeg` | JPEG |
| PNG | `image/png` | PNG |
| HEIC | `image/heic` | **PNG** |
| AVIF | `image/avif` | **PNG** |
| WebP | `image/png` | PNG |

対応していない形式を指定しても、ブラウザは例外を出さずに PNG を返す。
`blob.type` は指定した値をそのまま返すことがあるため、当てにならない。
アプリでは書き出したデータの先頭を読み、再度読み込めるかまで確認したうえで、
保存形式の選択肢を組み立てている。

### カメラの許可

アプリを完全に閉じてから開き直しても、ホーム画面に戻ってから開き直しても、
**毎回許可を求められた。** ページ側からこれを取り除く方法は無い。

### GPU

| 項目 | 結果 |
| --- | --- |
| WebGL2 | 使える |
| 浮動小数の描画先 | 使える |
| WebGPU | 使える |

## 計測の記録

### 2026-09-21 1 回目

最初の測定。4K が取得できること、`grabFrame` が遅いこと、`VideoFrame` が回転して返ること、
ズームとライトが使えることが分かった。

写真API は、能力値の最大（4032×3024）を指定したため `IPC Connection closed` で失敗し、
シャッター音の有無を確認できなかった。

この回の生データには `"image/heic": "image/heic"` という記録が残っているが、
**これは `blob.type` を見ただけの値で、中身は PNG だった。** 2 回目で訂正している。

この測定中に、合成した画像が上下反転する不具合が見つかった。原因は WebGL の仕様で、
ImageBitmap を入力にした `texImage2D` では `UNPACK_FLIP_Y_WEBGL` が無視される
（canvas や video 要素では有効になる）。合成処理は `createImageBitmap()` の結果を渡していたため、
GPU 側の原点と画像の原点が食い違っていた。処理の中で画像の座標系に変換する方式に改め、
入力の種類によらず同じ結果になるようにした。

端末チェックの照合が canvas だけを入力にしていたため、この不具合を見逃していた。
ImageBitmap を入力にした照合を追加し、修正を戻すと差が 140 になることを確認した。

### 2026-09-21 2 回目

大きさを指定しない写真API の撮影が成功し、**シャッター音が鳴らないことを確認した。**
所要時間は 1303 ミリ秒、解像度は映像と同じ 480×640、JPEG の大きさは 227KB だった。
端末の上限を指定した場合は、引き続き `IPC Connection closed` で失敗した。

上下反転の修正を確認した。canvas と ImageBitmap のどちらを入力にしても差は 0 で、
上下を反転させた場合との差は 141 だった（1 回目の測定では 140）。

書き出せる形式を中身まで確認し、HEIC と AVIF は PNG になることが分かった。

### 2026-09-21 3 回目

720p、1080p、4K の 3 段階で、写真API と通常撮影を比較した。結果は前掲のとおりである。
写真API はどの解像度でも音が鳴らなかった。指定できる大きさの上限も調べた。

この結果をもとに、既定の撮影方法を通常撮影のままとし、
「写真API で最大解像度を要求する」という設定項目を削除した。

## 測り方

1. `diag.html`（端末チェック）を https で開く。
2. 上から順に実行する。写真API の項目は、音が鳴るかどうかを自分の耳で確かめて記録する。
3. 比較の項目は、端末を机などに置いて固定し、明るさの変わらないものに向けてから実行する。
4. 「結果をコピー」で JSON を取り出し、この文書に追記する。
   `deviceId` と `groupId` は端末ごとの識別子なので、公開する前に伏せる。
